\begin{abstract}
Measuring complexity from a model's own code is biased by failure: a hard prompt can produce a short, broken program that looks simple. We instead score each prompt's structure on six dimensions from the prompt alone, never from generated code or test results. We draw 5{,}000 Python prompts across six bands of a preliminary single-rater score, and four out-of-panel LLM judges rescore every prompt (19{,}997 scores; composite ICC $=0.872$ on the 4{,}998 prompts with all four). Twenty-one models answer every prompt (105{,}000 generations), and an independent LLM auditor, checked against known-answer cases, reviews each unit-test verdict. Averaged over models, pass rate has a nonmonotone breakpoint at composite $\hat{\gamma}=14.0$: 83.4\% at or below, 90.1\% above. That jump is not a law of difficulty. With task-type fixed effects the breakpoint stays at 14.0 but the adjusted jump shrinks from 6.8 to 0.4 points, and neither of the benchmark's two prompt sources reproduces the jump on its own. Nineteen models pass more often above their own breakpoint and two less often, and one of those two declines, Gemini 3.1 Pro Preview's, comes from 156 API calls that returned nothing. Kimi K2.5 shows the clearest decline: with a prompt-source control, and within the later source alone, its break is at 14.25, where its later-source pass rate falls from 0.848 to 0.808 (95\% interval $[14.00,14.75]$). A 365-prompt audit-clean extension matches the original raw test outcomes at bins 15 and 16 but adds only 14 prompts above bin 16. Among failed generations with measurable output complexity, 25.0\% pair a prompt composite above 8 with output complexity of at most 10, twice the share among passing ones. The pooled breakpoint moves to 11.25 on raw test outcomes and 13.75 under the reviewed version's partial audit. Human agreement with the index is moderate and rater-dependent, paraphrase and cross-language rescoring preserve its ordering, and overidentification tests reject the six dimensions as instruments, so we treat the composite as an index and make no causal claim. The contribution is a prompt-side way to locate where each model's pass rate changes and to test how much that depends on the prompt mix and on how success is scored.
\end{abstract}

\section{Introduction}
% =====================================================================

Code-generating LLMs are evaluated functionally: does the program pass its tests~\cite{chen2021evaluating,austin2021program,jimenez2023swebench}? That tells us how often a model succeeds, not how success changes with the structure a task demands. Two models with the same average pass rate can behave very differently on prompts that need interacting branches, data structures, edge cases, or multi-step algorithms.

The usual way to measure a task's complexity is after the fact, from the code the model wrote. But when a model fails, what it writes is often a short stub or a broken fragment with low measured cyclomatic complexity, so a demanding prompt can land in a low-complexity bin precisely because the model failed. That can flatten, shift, or hide the link between task structure and pass rate. We call it the \emph{Reverse Threshold Problem}: some of the ``simple'' code that fails is really hard tasks the model never finished. Counting keywords in the instruction avoids the problem but reduces structure to surface words. We instead ask a rubric six separate questions about branching, iteration, state, data structures, edge cases, and composition. It is still a proxy, but it looks only at the prompt, so a model's failure cannot leak into it.

We build the Complexity Kink benchmark around that separation. From OpenCodeInstruct~\cite{opencodeinst} we draw 5{,}000 Python prompts stratified on a preliminary single-rater score; four out-of-panel LLM judges rescore the locked prompts, 21 models each answer every prompt, and an independent auditor reviews every unit-test verdict. We then estimate where pass rate changes along the prompt score, for each model and for all models pooled, and ask how much each estimate depends on the model or pooling rule, the prompt source, the score, the generation settings, and the test protocol. We also report output-side comparisons and the instrumental-variable design behind the title, but its candidate instruments fail their joint exclusion restrictions, so we give them no causal reading.

The results do not support a universal cutoff. Averaged over models, pass rate falls through the middle of the index and rebounds in the high region, but task type and prompt source explain most of the jump: the two sources differ sharply in score and pass rate, and neither reproduces the pooled $+6.8$-point change. Nineteen model-specific fits are higher above their breakpoint and two lower, and one of the two comes from failed API calls. Kimi K2.5 gives the clearest decline, and it survives a prompt-source control and every outcome definition we tried. A matched extension agrees with the original data at bins 15 and 16, where it adds support, but the region above 16 is still too thin for a firm claim.

\vspace{2pt}
\noindent\textbf{Contributions.}
\begin{itemize}
\item We formalize failure-dependent output complexity and show it in this sample: 25.0\% of failed complete cases pair a structurally nontrivial prompt with generated-output cyclomatic complexity of at most 10.
\item We introduce an ensemble-scored prompt-side index and test it against human ratings, plain-language paraphrases, and Java and C++ re-expressions.
\item We release a 5{,}000-prompt Python benchmark with all judge scores, 105{,}000 generations, test outcomes, and audit verdicts,\footnote{Code and data: \codeurl{}.} and use it to estimate model-specific reliability breakpoints.
\item We stress-test those estimates under pooling, repeated sampling, task type, prompt source, outcome definition, and an audit-clean extension, and report when a breakpoint is composition-sensitive.
\end{itemize}

\section{Related Work}
% =====================================================================

\textbf{LLM code evaluation.} HumanEval~\cite{chen2021evaluating}, MBPP~\cite{austin2021program}, and SWE-Bench~\cite{jimenez2023swebench} established functional testing as the central protocol for code-generating LLMs; that functional outcome remains our target variable. We instead study how to measure the structure of the task being attempted. OpenCodeInstruct~\cite{opencodeinst} supplies instruction-code pairs, but reference code reflects one implementation rather than latent task structure.

\textbf{Complexity measurement and benchmark bias.} Cyclomatic complexity is computable from source code, from McCabe's formulation to static analyzers such as Lizard~\cite{mccabe1976complexity,lizard}. In code-generation evaluation the available source is often the model output, which makes the metric post-treatment: measured complexity depends on success or failure~\cite{montgomery2018posttreatment}. We score the prompt instead.

\textbf{Instrumental variables and threshold estimation.} IVs are a standard response to endogenous regressors~\cite{wooldridge2010econometric}, with weak-instrument and overidentification tests as essential diagnostics~\cite{stock2005testing,hansen1982large,bowsher2002reject}, and are increasingly used in empirical software engineering~\cite{grafvlachy2024cleaning,siebert2023applications}. Our rubric-dimension IV fits fail these diagnostics and are kept only as diagnostics; the primary analysis applies Hansen's threshold regression and bootstrap sup-Wald test~\cite{hansen2000sample} to the composite directly.

\textbf{LLMs as judges.} G-Eval~\cite{liu2023geval}, AlpacaEval~\cite{alpacaeval}, and MT-Bench~\cite{zheng2023judging} use LLMs to evaluate model outputs, building on rubric-based automatic evaluation in NLP~\cite{hashimoto2019unifying}. Our rubric judges score the input prompt, not an answer, against a published structural rubric, and they sit outside the evaluated panel: they measure a property of the input rather than grade an output. A separate LLM auditor reviews unit-test verdicts (Section~\ref{sec:data}).

\section{Background: Failure-Dependent Output Complexity}
% =====================================================================

Let $\kappa_i^*$ denote the latent structure required by task $i$, let $y_{im}$ denote the functional outcome for model $m$, and let $\kappa_{im}^{\mathrm{obs}}$ be the cyclomatic complexity measured on that model's generated output. Even a passing output is only one implementation of the task, so $\kappa_{im}^{\mathrm{obs}}$ need not equal $\kappa_i^*$. More importantly, the measurement itself depends on the outcome:
\begin{equation}
\kappa_{im}^{\mathrm{obs}} = g(\kappa_i^*, y_{im}, \eta_{im}),
\label{eq:failure-dependent}
\end{equation}
where failed generations often collapse to short programs with low measured complexity. Stratifying pass rate by $\kappa_{im}^{\mathrm{obs}}$ therefore conditions on a post-generation quantity affected by success.

We avoid this with a prompt-side index $C_i$ that depends only on the prompt, so it cannot depend on whether a model succeeded. (Our judges scored the prompts after most generations existed, but never saw them.) Our primary target is descriptive: the conditional relationship $\mathbb{E}[y_i\mid C_i]$ in the constructed benchmark, where $y_i$ is pass rate averaged over evaluated models. The six rubric dimensions could also serve as candidate instruments for $\kappa_i^{\mathrm{obs}}$, but a causal reading would need strong exclusion restrictions, and the diagnostics below reject them.

\section{Methodology}
% =====================================================================

\subsection{Data}\label{sec:data}
We use 5{,}000 Python tasks from OpenCodeInstruct~\cite{opencodeinst} from two sources, which we call construction frames: 2{,}246 prompts kept from an earlier stage, drawn from a 200{,}000-record source-ordered prefix, and 2{,}754 later candidates that passed automated contract and test-quality filtering and deliberately added high reference-complexity tasks. The earlier prompts never went through that filter: for 1{,}259 of them the source's own reference solution fails at least one unit test. A preliminary \texttt{o4-mini} rater scored candidates with the rubric below, and we sampled 834 prompts in each of the preliminary-score bands 0--3 and 4--6 and 833 in each of 7--9, 10--12, 13--15, and 16--24. That score was used for sampling only.

After the prompt set was locked, the four-judge ensemble rescored every prompt, from the prompt text alone, and every analysis uses that ensemble mean. On the bands $[0,3]$, $(3,6]$, $(6,9]$, $(9,12]$, $(12,15]$, $(15,24]$ the final index has 319, 943, 940, 898, 1{,}425, and 475 prompts: stratified by the preliminary score but not balanced on the final one, and unlike the natural OpenCodeInstruct distribution. Reference-solution cyclomatic complexity shaped the upstream pool and is used only for alignment checks.

The evaluated panel has 21 models: Claude Opus 4.6, Opus 4.7, and Sonnet 4.6; GPT-5.4, GPT-5-mini, GPT-4.1, GPT-OSS-20B, and GPT-OSS-120B; Gemini 3.1 Pro Preview and Gemini 3 Flash; Grok-3; DeepSeek V3.2; Kimi K2.5; Qwen 3.6 Plus and Qwen 3.5-9B; Mistral Large-3, Devstral Small 2505, and Ministral-3-14B-reasoning; Llama 3.3-70B; GLM 4.7-flash; and Trinity-large. No rubric judge is in the panel. Five open-weight models were served locally as 4- or 8-bit quantizations, and each model's two frames were generated in separate runs, weeks apart and sometimes through different routes or token limits; the release records routes, versions, and settings. A locally served, quantized AuroraGPT-IT-v4 run covered only the earlier frame and was excluded post hoc without a prespecified rule; its pass rate on that run's 5{,}000 prompts was 20.6\% under the reviewed version's outcome, and performance was not a documented exclusion criterion. Each model generated one solution per prompt ($21\times5{,}000=105{,}000$ generations).

Pass rate starts from the fraction of Nvidia-supplied unit tests passed. Because tests can reject valid code (say, a renamed function) or miss defects, MiMo-V2.6-Pro, an auditor from a vendor used nowhere else in the study, read each generation's task, code, tests, and harness result. A ``correct'' verdict sets pass rate to 1.0 and ``incorrect'' to 0.0; uncertain, unparseable, or cut-off responses (1.1\%) keep the harness value, and the 208 generations with no code count as failures. The outcome is therefore a binary verdict for 98.9\% of generations; mean pass is 0.851, against 0.792 on raw harness values. Appendix~\ref{app:outcome-audit} covers the known-answer checks, where selection departed from our protocol, second-auditor agreement, and the main analyses on raw harness outcomes and under the reviewed version's partial \texttt{o4-mini} audit. The pooled analysis averages pass rate over the 21 models within prompt ($N=5{,}000$); per-model analyses use the same 5{,}000 rows. Generated-output complexity is McCabe cyclomatic complexity from Lizard~\cite{lizard}, summed over the functions in the cleaned code; it exists for 103{,}948 generations, and analyses using it report complete-case denominators.

\subsection{Rubric Scoring}

Four out-of-panel LLM judges deployed through Azure AI Foundry, \texttt{o4-mini}, \texttt{gpt-5.5}, \texttt{llama-4-maverick}, and \texttt{command-a}, score every prompt with the same rubric prompt: 4{,}998 prompts have four scores, one has three, and one has two (19{,}997 score rows). We average each prompt-dimension pair across available judges; composite ICC is 0.872 on the 4{,}998 complete cases, and scorer disagreement is kept for diagnostics. Each prompt is scored on six dimensions, each $0$ to $4$ (Table~\ref{tab:complexity_dimensions}).
\begin{table}[h]
\caption{Complexity dimensions and scoring criteria.}
\label{tab:complexity_dimensions}
\centering
\begin{tabular}{p{3cm} p{4cm} p{5.5cm}}
\hline
\textbf{Dimension} & \textbf{Score = 0} & \textbf{Score = 4} \\
\hline
Branching & No conditionals & Deeply nested or combinatorial \\
Iteration & None & Nested recursion or complex multi-pass \\
State & Stateless or single variable & Concurrent state tracking \\
Data structures & Primitives only & Multiple interacting complex structures \\
Edge cases & None & Combinatorial interacting checks \\
Composition & Single operation & Pipeline of interdependent algorithms \\
\hline
\end{tabular}
\end{table}

The primary prompt-side index is $C_i = \sum_{d=1}^{6} Z_{i,d} \in [0,24]$, where $Z_{i,d}$ is the ensemble mean for dimension $d$. The dimension vector $\mathbf{Z}_i=(Z_{i,1},\ldots,Z_{i,6})$ is kept for interpretation, reliability analysis, and secondary IV diagnostics.

\textbf{Design decisions.} Separate dimensions make the index interpretable, show where raters disagree, allow per-dimension human calibration, and permit an overidentification test when treated as candidate IVs. The five-point scale leaves a neutral middle score for ambiguous prompts. Each dimension is anchored to expected solution structure and explicitly excludes LLM difficulty, code length, and language idioms, so the outcome is not built into the measure. Keeping the judges out of the evaluated panel reduces circularity but does not by itself establish accuracy, human agreement, or IV exclusion.

\subsection{Primary Breakpoint Analysis}
For a candidate breakpoint $\gamma$, we fit separate linear relationships on the two sides of the prompt-side composite:
\begin{equation}
\mathbb{E}[y_i\mid C_i] =
\begin{cases}
\alpha_1+\beta_1 C_i, & C_i\leq\gamma,\\
\alpha_2+\beta_2 C_i, & C_i>\gamma.
\end{cases}
\label{eq:threshold}
\end{equation}
The mean-pooled outcome averages pass rate over the 21 models within prompt ($N=5{,}000$); model-specific fits use the same index and tests, and we also report median pooling and 21 leave-one-model-out fits. Regime means (averages on each side of the break) describe a selection-stratified sample. A model's $\hat{\gamma}$ marks where its pass-rate curve changes on this benchmark; it is not a causal, universal, or deployment-level failure point, and we read direction from the average pass rate on each side, not from the test statistic.

To locate the breakpoint, we adapt Hansen's threshold-regression procedure~\cite{hansen2000sample}:
\begin{enumerate}
\item For each candidate $\gamma$ on a percentile-spaced grid over $C_i$, requiring at least 500 prompts on each side, we compare (\ref{eq:threshold}) with a single line using a Wald-type $F$-statistic $W(\gamma)$.
\item The supremum $W^* = \sup_\gamma W(\gamma)$ identifies the threshold $\hat{\gamma}$.
\item Under $H_0$ of no threshold, we use Rademacher wild-bootstrap residual resampling and recompute $W^*$ at each draw. A separate pairs bootstrap gives a percentile interval for $\hat{\gamma}$, which we treat as descriptive.
\end{enumerate}
We repeat the pooled search with nine task-type indicators and, separately, the frame indicator, in two ways: as ordinary additive fixed effects, where only the composite line may break, and, as in the reviewed version, letting the indicators' effects also differ on each side. For each we report the adjusted jump, the coefficient on $\mathbf{1}[C_i>\hat{\gamma}]$ in a regression on that indicator and the controls. We also compare frame-specific linear slopes and repeat the search within each frame, for the pooled fit and, post hoc, for models whose pass rate falls across their break. Bootstrap and placebo settings are in Appendix~\ref{app:robustness}.

\subsection{Output-Complexity and IV Diagnostics}\label{sec:hansen-j}
We first compare pass rate directly with generated-output complexity and count the reverse-threshold cell among failed generations. As a secondary diagnostic, we regress generated-output complexity on the six rubric dimensions and use the fitted value in a 2SLS pass-rate regression:
\begin{align}
\kappa_i^{\mathrm{obs}} &= \pi_0+\mathbf{Z}_i\boldsymbol{\pi}+\nu_i, \label{eq:stage1}\\
y_i &= \alpha+\beta\widehat{\kappa}_i+u_i. \label{eq:stage2}
\end{align}
We estimate these with \texttt{IV2SLS} from \texttt{linearmodels}~\cite{linearmodels} and report Sargan (five degrees of freedom) and robust Wooldridge overidentification tests, single-instrument fits, principal-component rotations, and post hoc subsets. These tests reject the full instrument set, so $\hat{\beta}$ is a diagnostic coefficient, not a causal estimate.

\subsection{Additional Robustness Designs}
After the initial analysis we added post hoc stress tests, none preregistered: a nine-category task taxonomy, the frame analyses above, a five-draw repeated-sampling subset, plain-language paraphrase and Java/C++ re-expression rescoring, a blind two-grader human calibration, a 365-prompt audit-clean high-complexity extension, and a reanalysis that treats generations with no API response as missing. Appendix~\ref{app:robustness-designs} details the designs, and Figure~\ref{fig:pipeline} there summarizes the workflow.

\section{Results}
% =====================================================================

\subsection{Alignment with Reference Complexity}

Reference-solution complexity helped build the candidate pool, so agreement with it is a sanity check, not independent validation. On all 5{,}000 prompts, the composite has Pearson $r=0.80$ and Spearman $\rho=0.81$ with reference $\kappa$, rising from 4.64 at $\kappa=1$ to 14.34 at $\kappa\in[21,50]$, though not at every adjacent bin (Appendix Table~\ref{tab:rubric-ref-cc}). At the low end, where failed stubs push output CC toward 1, the rubric separates $\kappa=1$ from $\kappa=2$ prompts ($+0.61$, $p=3.1\times10^{-4}$), driven by iteration, state, and branching. A lexical keyword baseline also separates them ($+0.58$, $p=2.4\times10^{-3}$; Appendix Table~\ref{tab:low-end-separation}), so the rubric does not beat every cheap proxy; its advantages are explicit structural dimensions, measurable rater uncertainty, and the calibration checks below.

\subsection{Rater and Measurement Calibration}

Beyond the four-judge ICC of 0.872, we ran a deliberately difficult human calibration with LLM scores hidden: the first author graded 200 prompts, roughly half sampled for high judge disagreement, and the second author graded 50 of them. On all 200, first-author agreement with the ensemble is Pearson $r=0.408$, Spearman $\rho=0.373$, ICC$(2,1)=0.395$, with mean offset $-1.18$ points; per-dimension Pearson correlations range from 0.249 to 0.484 and quadratic-weighted $\kappa$ from 0.217 to 0.435. On the shared 50, the graders correlate 0.561 with each other and 0.613 and 0.921 with the ensemble, with offsets $-0.69$ and $-1.35$. These are stress-test estimates with substantial rater variation, not a human ground truth.

Two checks ask whether the index follows presentation rather than structure. Across 150 plain-language rewrites, ranks barely move (Spearman $\rho=0.963$); the mean shift is small ($-0.115$) but detectable (paired $p=0.031$), and 91.3\% of pairs are within one point. The rewrites were not verified by execution, so this shows score stability under a preservation instruction, not semantic equivalence. For 117 prompts re-expressed in Java and C++, the composite correlates 0.992 and 0.969 with Python, with inter-judge ICC 0.912 (Python), 0.913 (Java), and 0.882 (C++): evidence that scores transfer, not that non-Python generation is reliable.

\subsection{Generated-Output Complexity Misses the Prompt-Side Pattern}

Figure~\ref{fig:output-cc} plots pass rate against the Lizard complexity of the generated code: the curve is nonmonotone, with no clean decline. Among the 14{,}247 failed generations (outcome 0) with a computable Lizard value, 3{,}561 (25.0\%) have prompt composite $>8$ but output CC $\leq10$, twice the share among passing generations (12.2\%). The shares are 25.0\%, 25.2\%, and 25.4\% if ``failed'' means pass rate at most 0.25, 0.50, or 0.65. An automated pipeline would quietly file these demanding prompts as simple. Another 969 failed generations have no computable output CC and are left out.

\subsection{The Mean-Pooled Breakpoint}

Averaged over models, the sup-Wald search selects $\hat{\gamma}=14.0$ on the prompt composite (sup-Wald $=151.15$). None of 2{,}000 wild-bootstrap draws or 2{,}000 shuffled-index placebo draws reaches it ($p_{\mathrm{MC}}\leq1/2001<0.001$ each). The 3{,}703 prompts at or below $\hat{\gamma}$ average 83.4\% pass; the 1{,}297 above average 90.1\%. This is not a monotone collapse: pass rate falls through the middle of the index to a trough near composite 10, rebounds to a peak at bin 15, and falls again in the sparse bins above. By BIC the piecewise form beats linear and cubic fits ($-67$ versus 209 and 33).

The 95\% pairs-bootstrap interval, $[10.5,14.25]$, spans the stretch between the trough and the peak in Figure~\ref{fig:kink}. The estimate describes this constructed benchmark, not a point at which harder prompts become easier.

\subsection{Task-Type and Construction-Frame Sensitivity}\label{sec:frame}

We label all 5{,}000 prompts with a nine-category taxonomy fixed before labeling; one out-of-panel judge labels every prompt, and three more label a shared 500-prompt subset (Krippendorff $\alpha=0.787$). With task-type fixed effects the breakpoint stays at 14.0 and the search still finds a break there (sup-Wald 78.6; 0 of 300 wild-bootstrap draws exceed it), but the task-adjusted jump across it is only $+0.4$ points ($p=0.66$), against $+6.8$ unadjusted (Table~\ref{tab:task-type}). The reason is plain: 91\% of prompts above 14.0 are data-structures/algorithms tasks, against 22\% below. Letting task effects also differ by side moves the break to 11.5, where the raw gap is 2.1 points. A piecewise term at 11.5 raises predictive $R^2$ from 0.093 for task type alone to 0.160, which is incremental fit, not causal independence. Four of five large task categories still reject the full IV restrictions, so task type does not explain away the overidentification failure.

The construction frames tell a similar story. The 2{,}246 earlier prompts average composite 7.92 and pass rate 0.795; the 2{,}754 later ones, 11.42 and 0.897. A frame fixed effect leaves the break at 14.25 but cuts the adjusted jump to 1.8 points, and with both controls it turns slightly negative. Within frames, the earlier frame's best split, 9.50, is not significant (sup-Wald 4.02, bootstrap $p=0.14$) and a straight line fits better by BIC; the later frame breaks at 14.25 (sup-Wald 93.70, $p_{\mathrm{MC}}\leq1/301$) but rises only 1.8 points (0.890 to 0.908). Later prompts are 41.0\% of those at or below the pooled break and 95.4\% of those above it. So the dip and rebound are real features of this benchmark, but the big jump mostly reflects which source dominates the high region. The frame also marks separate generation runs and the test-quality difference noted in Section~\ref{sec:data}, so it is not purely a difference in prompts.

\subsection{Model and Pooling Heterogeneity}

Model-specific thresholds range from 10.0 to 14.25 (median 10.75). Nineteen models have higher mean pass above their own breakpoint and two lower: Kimi K2.5 (0.817 to 0.801 at 14.0) and Gemini 3.1 Pro Preview (0.872 to 0.793 at 10.75). Gemini's decline comes from 156 generations for which the API returned nothing (time-outs and empty responses in one batch, 144 of them at composite $>14$). Treated as missing rather than as failures, they turn Gemini's contrast upward (0.859 to 0.876 at 14.25), leave a small later-frame decline (0.890 to 0.869), and leave the pooled result unchanged (14.0; 0.834 to 0.907; Appendix~\ref{app:no-response}). How many models decline also depends on the outcome: five under the reviewed version's audit and one on raw test outcomes (Appendix~\ref{app:outcome-audit}).

Kimi K2.5 is the clearest decline. With a frame fixed effect its search selects 14.25 (sup-Wald 45.5; 0 of 300 bootstrap draws exceed it), and so does a separate search within the later frame (sup-Wald 41.62), where its pass rate falls from 0.848 to 0.808 (95\% pairs-bootstrap interval $[14.00,14.75]$, whose upper end is the largest split the 500-prompt minimum allows). Piecewise BIC is 2{,}284 against 2{,}350 for a line. The earlier Kimi frame shows no significant break ($p_{\mathrm{MC}}=0.226$). Both 14.25 selections hold on raw test outcomes and under the reviewed audit.

The same prompts, scores, and tests are reused, so these are comparisons, not independent replications. The pooled threshold stays at 14.0 in all 21 leave-one-model-out fits; median pooling selects 10.5 and narrows the gap to 2.9 points (0.879 to 0.908). Details are in Appendix~\ref{app:per-model}; a library-mention diagnostic on a separate sample is in Appendix~\ref{app:library}.

We separately selected high-composite candidates on the prompt side only, audited their contracts, and kept only prompts whose reference solution passes every test: 365 new prompts, 218/133/11/3 at display bins 15/16/17/18. Two caveats apply. Its generated code was not saved, so it could not be audited and we compare raw test outcomes on both sides. And it was generated under a different protocol, at temperature 0 with a system prompt that names the functions to define, which by itself can raise raw pass rates by removing naming failures. To hold the model mix fixed, Figure~\ref{fig:tail-extension} uses the five models in both runs. At bin 15 the extension and original means are 0.880 and 0.890; at bin 16, 0.799 and 0.795 (differences $-0.009$ and $+0.004$; Welch $p=0.554$ and $0.906$). \subsection{Repeated-Sampling Robustness}

On a 359-prompt, four-model subset with five draws per prompt-model cell at temperature 0.8 (7{,}180 generations on raw test outcomes; these were not part of the audit), the mean within-cell standard deviation is 0.064 and the median is zero. Requiring at least 59 prompts per side (a sixth of the subset), the first draw and the five-draw mean both select $\hat{\gamma}=14.25$. Their correlation, 0.960, is a part-whole comparison, since the first draw is in the mean. This supports a stable threshold location for the sampled subset, not universal single-draw reliability.

% =====================================================================
\section{Discussion}
% =====================================================================

\textbf{The IV diagnostics.} The six-dimension IV specification does not support causal identification. Sargan $J=552.16$ on five degrees of freedom and the robust Wooldridge statistic (408.52) reject at machine precision, and not because of sample size: mean $J$ is already 33.4 at $n=250$ (null expectation about five), where every random subsample rejects. Single-instrument estimates disagree in sign (data structures $+0.0022$; state $-0.0040$; composition $-0.0045$), rotating the dimensions does not fix that, and the few passing subsets were picked after seeing the data (Appendix~\ref{app:econ-diagnostics}). What survives is the composite as an index measured from the prompt alone: output failure cannot reach it, and it can be checked directly against reference CC, human ratings, paraphrases, and re-expressions. None of those checks makes it an instrument.

\textbf{What the breakpoint means.} The pooled breakpoint compactly describes a nonmonotone curve in a selection-stratified benchmark; it is not a universal difficulty limit. Task-type fixed effects keep its location but remove nearly all of its jump, neither frame reproduces the jump, median pooling moves it to 10.5, the outcome definition moves it between 11.25 and 14.0, and model directions differ. Leave-one-model-out stability shows that no single model drives it, not that it is independent of pooling, composition, or the outcome definition. Kimi K2.5 is the clearest downward, benchmark-conditional case: its later-frame break and decline hold under all three outcome definitions. A model's $\hat{\gamma}$ is therefore a candidate reliability breakpoint for that model under this frame, index, generation setting, and test protocol. The extension adds evidence only where it adds support: on raw outcomes it matches bins 15 and 16, and the tail beyond them is open.

\textbf{Why a prompt-side index, and implications.} The central design choice is what the index is allowed to see: the input only, never the output. A lexical proxy shares that advantage and may be preferable when transparency or cost matters most; the rubric trades cost for interpretable dimensions and measurable rater disagreement, and the two-grader calibration argues for reporting that uncertainty rather than trusting any single rater. The idea may carry beyond Python, but our evidence covers only score transfer to Java and C++. If you bin results by output complexity, say how failed and missing outputs are counted. Prompt-side scores can help, as long as you also show how prompts were sampled, how reliable the raters are, how many prompts each bin holds, and pooled and task-adjusted results. They are diagnostic summaries, not deployment rules, until validated prospectively.

% =====================================================================
\section{Limitations}
\label{sec:limitations}
% =====================================================================

\textbf{Constructed sampling frame.} The benchmark is balanced on a preliminary single-rater score, not the final index, and inherits a 200{,}000-record prefix scan and deliberate high-reference-complexity supplementation. The two frames differ sharply in score, pass rate, test quality, and generation run, and their changing mixture explains much of the pooled rebound. The benchmark does not estimate performance under the natural OpenCodeInstruct distribution, and every estimate is conditional on the model or pooling rule, frame, index, generation settings, and test protocol.

\textbf{Composition and pooling.} Task-type controls remove most of the pooled jump, the within-frame changes are small or not significant, and median pooling moves the break; read the pooled 14.0 only with those sensitivities.

\textbf{Outcome definition.} The outcome depends on one LLM auditor, adopted by author decision after no candidate met our pre-declared rule: it missed the clean-accuracy threshold by three cases during selection, then met every threshold on a fresh set, a check that no longer gated adoption. A second auditor agrees with it at $\kappa=0.631$, and its known-answer accuracy is measured against labels that are themselves noisy. The extension and repeated-sampling checks use raw test outcomes, and the 157 generations with no API response count as failures (Appendices~\ref{app:outcome-audit} and~\ref{app:no-response}).

\textbf{Scorer dependence and human disagreement.} Common-mode LLM bias can carry into the index, and the judges are out-of-panel but not out-of-family (GPT-5.5 and Llama 4 share developers with panel models); the ensemble makes disagreement visible but cannot remove it. Human-LLM agreement is only moderate on the disagreement-enriched sample and varies by rater.

\textbf{No causal IV claim.} The overidentification restrictions reject even in small subsamples and the candidate instruments imply conflicting coefficients, so the 2SLS fits cannot identify a causal effect.

\textbf{Scope.} AuroraGPT-IT-v4 was excluded post hoc without a prespecified rule, so a like-for-like 22-model sensitivity is unavailable. The extension adds 351 prompts at bins 15 and 16 but only 14 above 16, leaving that endpoint underpowered. Generation and execution are Python-only; the Java and C++ results test score transfer only. The task taxonomy, frame analyses, extension, human, paraphrase, language, and repeated-sampling checks were added post hoc and not preregistered, and we do not track prompts or model families over time.

% =====================================================================
\section{Conclusion}
% =====================================================================

Generated-output cyclomatic complexity is a poor stand-in for prompt structure when failures produce short or unscorable programs. A prompt-side index avoids that problem and supports model-specific breakpoint estimation; the clearest downward example is Kimi K2.5 near 14.25, which holds under a frame control, within the later frame, and across outcome definitions. The pooled result is less stable: task type removes most of its jump, the prompt source explains the rebound, and pooling and the outcome definition move it. The extension matches bins 15 and 16 on raw outcomes, human calibration is moderate, paraphrase, language, and repeated-sampling checks preserve ordering and location, and the candidate instruments fail their joint restrictions, so the contribution is measurement and observational analysis, not causal identification. The lesson for benchmark designers is modest: add prompt-only measures to output-derived ones, publish the rubric and rater uncertainty, show support counts, and report how composition, pooling, and the outcome definition change the curve.

\section{Reverse-threshold and Robustness Details}
\label{app:robustness}

\subsection{Bootstrap and placebo settings}

The mean-pooled analysis uses 2{,}000 wild-bootstrap draws, 1{,}000 pairs-bootstrap draws for the interval, and 2{,}000 shuffled-index placebo draws. Unadjusted model-specific fits use 500 wild-bootstrap and 500 placebo draws. Every controlled search, additive or differing by side, pooled or model-specific, uses a 300-draw wild bootstrap under its own no-break model (seed 42), and the within-frame threshold intervals use 300 pairs-bootstrap resamples. Pairs-bootstrap intervals are percentile intervals and are descriptive: for a threshold location they are not guaranteed to have nominal coverage, and the headline bootstrap distribution is bimodal (most draws at 14.0, a smaller mode near 10.5). The repeated-sampling search on 359 prompts requires at least 59 prompts on each side (one sixth of the subset) instead of 500.

\subsection{Task-type and control specifications}

The nine fixed categories contain 2{,}005 data-structures/algorithms prompts, 654 array/matrix/grid, 619 numeric/math, 617 string/text, 341 other, 276 stateful simulation, 215 parsing/serialization, 190 logic/validation, and 83 API/library orchestration prompts. On the shared 500-prompt reliability set, pairwise Cohen $\kappa$ ranges from 0.737 to 0.856 and Krippendorff $\alpha=0.787$.

The two control specifications answer different questions. With additive fixed effects the break model is $y_i=\alpha+\beta C_i+\mathbf{x}_i'\boldsymbol{\delta}+\mathbf{1}[C_i>\gamma](\alpha'+\beta'(C_i-\gamma))+u_i$, so only the composite line may break. The by-side specification (the reviewed version's) fits separate regressions, controls included, on each side, so its test also asks whether task or frame effects differ across the break; that is why it moves the task-controlled break to 11.5 (where the task-adjusted jump is $-6.2$ points) and, under the reviewed and raw-harness outcomes, the frame-controlled break to 8.50 (Table~\ref{tab:outcome-sensitivity}). By side, the frame-controlled search selects 14.25 (sup-Wald 59.0). Adjusted jumps at the unadjusted $\hat{\gamma}=14.0$ are $+6.8$ with no controls, $+0.4$ with task type ($p=0.66$), $+1.6$ with the frame ($p=0.03$), and $-2.8$ with both ($p=0.001$).

The piecewise composite at 11.5 has $R^2=0.04530$ alone. Task-type fixed effects have $R^2=0.09285$ alone, and their combination has $R^2=0.16010$. Thus the piecewise term adds 0.06725 in-sample predictive $R^2$ beyond the labels. Table~\ref{tab:within-type-j} shows that the IV failure is not localized to one task category.

\section{Outcome audit}
\label{app:outcome-audit}

\textbf{Why the outcome is audited.} A unit-test verdict can be wrong in both directions: the supplied tests call specific function names and expect exact output formats, so valid code can fail them, while weak tests can pass defective code. The reviewed version of this paper asked \texttt{o4-mini} whether each harness verdict was right on the merits, given the task, code, tests, and harness pass rate, and to treat function-name mismatches, script-style input and output, and formatting differences as correct; ``correct'' set the pass rate to 1.0, ``incorrect'' to 0.0, and ``uncertain'' kept the harness value. That audit covered only the 2{,}246 earlier-frame prompts, where it gave a definite verdict for 46{,}706 of 47{,}166 generations (15{,}725 rose to 1.0 and 8{,}123 fell to 0.0) and ``uncertain'' for 92 more. Its outcome definition therefore coincided with the construction-frame indicator, and \texttt{o4-mini} is also a rubric judge. For this version, one auditor from a vendor used nowhere else in the study (not a rubric judge, an evaluated model, or the paraphraser) reviewed every generation with code, using the same system prompt, inputs, and verdict mapping.

\textbf{Selection protocol.} A protocol written before any auditor was scored fixed a known-answer set and a selection rule. The set draws 150 benchmark prompts, stratified across display bins, whose reference solution passes every unit test, and builds three cases from each, all executed in the benchmark harness inside a network-isolated container: the normalized reference (clean; correct), a copy with the test-called functions renamed so that the harness fails it (cosmetic; correct), and the most subtle single AST mutation that the tests detect (bug; incorrect). An auditor is eligible if at most 2\% of its responses are unparseable or failed, it judges at least 95\% of clean cases correct, and it rescues at least 90\% of cosmetic cases; among eligible auditors, the lowest wrong-rescue rate on bugs wins.

\textbf{How selection actually went.} Five dated amendments are recorded in the repository, which also collects every departure from the protocol. (i) Before any pilot case was scored, a smoke test showed one candidate misreading the closing format reminder, so the reminder was reworded identically for all auditors and the token cap raised to 16{,}000. (ii) Neither Azure-deployed candidate was eligible (Table~\ref{tab:auditor-pilot}), so we extended the pool to hosted models from unused vendors, to be run in a listed order, and required that a selected auditor also meet the rule on a fresh, disjoint known-answer set at the production endpoint. Only the first two listed candidates were run, and both failed; we then added MiMo-V2.6-Pro, which was not on the list, and the other three listed candidates were never run. (iii) MiMo-V2.6-Pro had the highest overall accuracy and the best cosmetic rescue but judged 140 of 150 clean references correct against the required 143. No candidate met the rule, and we adopted it by author decision before its fresh-set result existed, which made that confirmation report-only. It then met every threshold on the fresh set, with clean accuracy exactly at the minimum. (iv) Generations with no code are marked incorrect by rule without a request, a behavior of the audit client that the protocol did not state. Amendment~5, added after production when a review of the pipeline found that the parser could read a verdict from a response cut off mid-reasoning, stops counting responses cut off by the token limit or a content filter: 9 of MiMo-V2.6-Pro's production verdicts now keep the harness value, and among the pilot rows only Phi-4-reasoning's changes.

\textbf{What the known-answer rates mean.} The rates measure agreement with labels that come from the harness and from how the cases were built, not from human review, and those labels are noisy in both directions. Thirty-five of the 150 clean references in set A are rejected by at least one auditor in Table~\ref{tab:auditor-pilot}, some for violating an explicit task instruction the tests do not check, and at least one other auditor also rejects 7 of the 9 references that MiMo-V2.6-Pro rejects. Conversely, some clean references are defective in ways the tests miss (for example, a JSON parser that does not decode string escapes), and an auditor that accepts them is credited as correct. No human review of the disputed references was performed. The cases are also synthetic renamings and single mutations, which may be easier than real model failures, and an auditor that rescues renamed or reformatted code can also rescue code the tests correctly reject (1.3\% and 0.7\% of bugs on the two sets).

The five locally served models are GPT-OSS-20B, Qwen 3.5-9B, Ministral-3-14B-reasoning, and Devstral Small 2505 (4-bit GGUF) and GLM 4.7-flash (8-bit).

\textbf{Code.} The repository (\codeurl{}) contains the six-dimension rubric prompt, model metadata, the outcome-audit code and protocol, and analysis scripts for the breakpoint, control, construction-frame, diagnostic-IV, placebo, and figure pipelines, together with locked summary outputs and the source tables for every figure. \texttt{scripts/camera\_ready/run\_reanalysis.sh} regenerates every outcome-dependent result for a chosen outcome definition. Re-running model inference or the audit requires provider access; the human-calibration, paraphrase, cross-language, and repeated-sampling statistics can be recomputed from the released tables.

Generated-output cyclomatic complexity is computed with Lizard 1.21.0 under the MIT License~\cite{lizard}; diagnostic IV estimation uses \texttt{linearmodels} 7.0 under the NCSA License~\cite{linearmodels}. The code repository is released under the MIT License.

\textbf{Compute.} The main compute cost is inference: four rubric judges score 5{,}000 prompts each, and 21 evaluated models each generate one answer for every prompt. Open-weight or locally served models are run one model at a time on A100-class GPU workers; serverless/API models are run through provider batch or hosted inference endpoints. The outcome audit sends one request per generation with code to a hosted auditor (104{,}792 production requests before retries, plus 450 known-answer cases per auditor per set and 5{,}240 agreement-sample requests per second auditor). Unit-test execution, Lizard scoring, and econometric analysis run on CPU workers. Exact wall times, worker memory, and total compute were not logged consistently across providers, so we do not claim a complete compute accounting.

\textbf{Execution safeguards.} Generated code is executed only by the benchmark unit-test harness, one test assertion per fresh Python process in isolated mode with a 5-second timeout. The harness itself does not isolate the file system or the network; the audit's known-answer variants ran in the same harness inside a container without network access, and the auditor reads code but never executes it. The artifact does not release a trained model or a public code-generation service.

\textbf{LLM usage.} LLMs are part of the core methodology as rubric judges, as evaluated code-generation models, and as the outcome auditor. LLM-assisted drafting, editing, and independent auditing of the analysis code were also used under author supervision; all scientific claims, analysis choices, and final text remain the authors' responsibility.
